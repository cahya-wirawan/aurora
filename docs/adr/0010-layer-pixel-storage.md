# 0010. Layer pixel storage: one shared `TileStore` per document, addressed by surface

**Status:** Accepted
**Date:** 2026-08-06
**Deciders:** Cahya Wirawan
**Related:** PRD §6 (*Unlimited layers and history*), invariant §7.3.1 (*all pixel access goes through the tile store*), invariant §7.3.5 (*brush input bypasses the general graph via a scratch layer*), ADR 0005 (tile size/scratch-disk budget), ADR 0009 (`.aur` document format — names this exact question as unresolved follow-on work), PLAN.md M1.4, M1.9 (basic tools, basic brush/eraser)

## Context

`aurora_doc::LayerKind::Pixel` has carried a `bounds: Rect` field with no real pixel storage behind it since M1.4, and that type's own doc comment has named the reason precisely: "whether pixel storage is one store per layer (simple, but an unlimited-layers document would mean an unlimited number of background-writer threads, since `TileStore::new` spawns one) or one shared store addressed some other way is a real resource-management question this pass deliberately leaves open rather than picking silently." Two subsystems hit this wall from the other side while trying to move past it: PLAN.md M1.9's "basic tools" bullet couldn't give the Move tool anything to reposition (no pixel content exists to move), and its "basic brush and eraser" bullet built real, tested dab-spacing logic (`aurora_brush::dabs_along_path`) but stopped exactly at the point of stamping a dab into an actual pixel, for the same reason. ADR 0009 (`.aur` document format) already named this as its own unresolved follow-on: the manifest's per-layer tile-addressing scheme needs an answer to this question before it can be finalized.

Three facts from the existing, already-implemented `aurora-tile` crate shape the answer:

1. **`TileStore::new` spawns one dedicated `std::thread` (the background writer) and owns one `scratch_dir`.** This is real, not hypothetical — `crates/aurora-tile/src/writer.rs`'s `BackgroundWriter::spawn` calls `std::thread::spawn` unconditionally. PRD §6 requires "unlimited layers" as a headline scalability property; one `TileStore` per layer would mean one OS thread per layer, unboundedly, which directly contradicts that requirement at scale (hundreds of pixel layers is a realistic professional document, not an edge case).
2. **`TileStore`'s own LRU budget is meant to bound total resident memory**, not memory-per-something-else (ADR 0005: "the budget is tile-count-based... enforced by evicting the least-recently-used resident tile whenever a page-in or new-tile allocation would exceed it"). Splitting the budget across N per-layer stores means either each store gets a shrinking fraction of the real budget as layers are added (with no API today to resize a live `LruCache`'s capacity) or each gets the *full* budget independently, silently multiplying real resident memory by the layer count — either way, the one property this budget model exists to guarantee (bounded total memory) breaks.
3. **Invariant §7.3.1 already says "the tile store," singular** — "all pixel access goes through the tile store." The invariant was written assuming one store, not one instantiated per layer.

`spike/vertical-slice` already measured a working design for the one genuinely latency-sensitive piece of this: the active brush stroke. Its `Document` (`spike/vertical-slice/src/doc.rs`) uses **two** `TileStore`s — a `base` store for the document's own settled content, and a small, separately budgeted `stroke` store (`budget_bytes / 8`) for the in-progress stroke only, merged into `base` and recreated fresh on `end_stroke`. `spike/FINDINGS.md`'s own p99 stroke latency (9.1 ms against a 10 ms budget — under 1 ms of margin) was measured with this split in place. Mixing the active stroke's tiles into the same eviction/paging path as the rest of the document's tiles is untested and risky: a large pan or a big multi-layer composite elsewhere in the document could evict the very tile the pointer is actively painting into, turning a stroke's next dab into a synchronous disk read inside a budget with no room for one.

## Decision

**One shared `aurora_tile::TileStore` per open document** holds every real (non-scratch) pixel layer's tiles — one background-writer thread and one LRU budget for the whole document, not one per layer, directly closing the "unlimited layers → unlimited threads" gap.

**Tiles are addressed by a compound `(SurfaceId, TileId)` key**, not `TileId` alone. `SurfaceId` is a new type in `aurora-tile`, built the same way `aurora_doc::LayerId` already is — a marker struct plus `aurora_core::Id<Surface>` — living in `aurora-tile` (not `aurora-core`) because it is meaningless outside tile addressing, the same reasoning that keeps `LayerId` itself defined in `aurora-doc` rather than `aurora-core`. `TileId` itself is unchanged (still a plain grid position within *a* surface); `SurfaceId` is the "which surface" half, added only at `TileStore`'s own API boundary (`get`/`get_mut`/`take_dirty` all gain a `SurfaceId` parameter; the resident `LruCache` and `paged_out` map are keyed on the pair; eviction picks the globally least-recently-used `(SurfaceId, TileId)` regardless of which surface it belongs to — the *correct* behaviour for a memory bound that is supposed to cover the whole document, not just whichever layer happens to be active).

**`SurfaceId` values are reused from `LayerId`, never independently generated.** `aurora-doc` (which already depends on `aurora-tile` per `scripts/layering.json`) converts a pixel layer's own `LayerId` into a `SurfaceId` via `SurfaceId::from_raw(layer_id.to_raw())` when it first touches that layer's storage — no second `IdGenerator`, no separate allocation table to keep in sync, and no risk of the two id spaces colliding, since there is only ever one generator (`aurora_doc`'s own `IdGenerator<Layer>`) producing the underlying numbers. A `LayerKind::Group` layer never needs a `SurfaceId` at all — it owns no pixels — so nothing is allocated for it, matching `TileStore`'s existing "sparse, created lazily on first touch" design.

**The active brush/eraser stroke keeps its own separate, small `TileStore`** — not a surface inside the shared document store — matching `spike/vertical-slice`'s own already-measured, proven split (invariant §7.3.5's "scratch layer" is this store). Created when a stroke begins, merged into the shared document store and torn down when it ends, the same `begin_stroke`/`end_stroke` shape the spike already validated. At most one exists per document at a time — this does not reintroduce the one-store-per-layer thread problem, since it is bounded by concurrent strokes (always one), not by layer count.

## Alternatives considered

**One `TileStore` per layer.** The status quo ante this ADR resolves. Simple to reason about individually, but rejected for the reasons in Context: unbounded background-writer threads as layer count grows, and a real memory-budget model that stops meaning what it says once split (or duplicated) across an unbounded number of stores.

**One shared store for absolutely everything, including the active stroke** (no separate scratch store). Rejected: no isolation between the stroke's own tiles and the rest of the document's eviction/paging traffic, when the one number that exists for this (`spike/FINDINGS.md`'s 9.1 ms p99, under 1 ms of margin against the 10 ms budget) was measured with that isolation in place. Removing it is not a proven-safe simplification; it is an untested regression risk against the tightest latency budget in the project.

**Encoding layer identity into `TileId`'s own `x`/`y` fields** (e.g. bit-packing a layer index into the high bits of each coordinate) instead of a proper compound key. Rejected: fragile (silently limits either the addressable layer count or the addressable canvas extent to whatever bits are left over — in tension with ADR 0002's 300,000 px ceiling, which already wants the full range of a `u32` grid coordinate), and it would smuggle a layering concept into a type (`TileId`) whose whole job is "a grid position, nothing else." A separate, explicit `SurfaceId` at the store's API boundary is clearer and costs nothing at the scale this project operates at (`Id<T>` is a plain `u64` underneath).

## Consequences

**Gained:** a real answer to the exact question `LayerKind::Pixel`'s own doc comment has posed since M1.4, unblocking the Move tool (something to reposition) and brush/eraser (somewhere to stamp a dab) — both currently stopped at this precise wall (PLAN.md M1.9). One background-writer thread and one real, meaningful memory bound per open document, regardless of layer count, matching PRD §6's "unlimited layers" without silently breaking the memory-budget guarantee ADR 0005 built. `SurfaceId` reuse from `LayerId` means no new id-allocation bookkeeping in `aurora-doc`. ADR 0009's own named follow-on (the `.aur` manifest's per-layer tile-addressing scheme) now has a direct answer: a tile's ZIP entry name carries its `(SurfaceId, TileId)` pair, and `SurfaceId` already equals the owning layer's own `LayerId`.

**Cost:** `aurora-tile`'s public `TileStore` API changes (every tile-access method gains a `SurfaceId` parameter) — real, mechanical churn in that crate's own tests, and in anything already calling it (nothing outside `aurora-tile`'s own tests does, today). The scratch-store/shared-store split is two pieces of state to keep synchronized correctly at stroke boundaries (merge-then-teardown), the same complexity the spike already carried, not new complexity this ADR introduces. A single shared store's one background-writer thread is a single point of contention for *all* eviction writes in a document — acceptable (this is exactly what the existing thread already does for one layer's worth of tiles; this ADR just widens what flows through it), but worth naming: a pathological all-layers-dirty-at-once scenario now funnels through one write queue instead of many, which was already true in practice since `spike/vertical-slice` never ran more than one store's worth of real paging load at a time either.

**Follow-on work:** the actual code — `SurfaceId`/`Surface` and the `TileStore` API change in `aurora-tile`; deciding which `aurora-doc` type actually owns the shared store instance (most likely a new field on `LayerTree`, or a small wrapping type bundling `LayerTree` + the store + `SelectionSet` + `History` — this ADR decides the storage model, not `aurora-doc`'s own type layout); wiring `aurora_brush::dabs_along_path`'s output into real dab-stamping against the scratch store; the Move tool's own still-separate blocker (an active-layer selection mechanism, PLAN.md M1.9) is unaffected by this ADR and remains open; the `.aur` manifest's exact `(SurfaceId, TileId)` → ZIP-entry-name convention (ADR 0009's own follow-on, now unblocked).

## Reconsider if…

- A real multi-threaded write workload (e.g. background export while painting) shows one shared writer thread/queue is an actual throughput bottleneck, not just a theoretical one — a worker-pool `BackgroundWriter` would be a real, separate change to make at that point, not one to speculate on now
- The scratch store's own merge-on-`end_stroke` step (moving tiles from the stroke store into the shared document store) turns out to cost enough to matter at the brush's own latency budget — untested; the spike measured the *painting* half of this, not a shared-store-aware merge step, since the spike's own `base`/`stroke` stores never needed to reconcile addressing with a compound key
- `LayerKind::Group`'s own future evolution (e.g. group-level effects/clipping needing group-level raster buffers) turns out to need pixel storage after all, at which point group layers would need `SurfaceId`s too — not something this ADR forecloses, just not needed yet
