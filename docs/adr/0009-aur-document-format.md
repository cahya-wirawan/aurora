# 0009. `.aur` document format: a ZIP container, `postcard` metadata, embedded tile codec

**Status:** Accepted
**Date:** 2026-08-06
**Deciders:** Cahya Wirawan
**Specification:** [`docs/aur-format.md`](../aur-format.md) is the byte-level description of the format as implemented (derived from the code; where it disagrees with this ADR the code wins).
**Related:** PRD §8.1, §12 Q7, §14 ("`.aur` is an open format"); ADR 0002 (300,000 px ceiling); ADR 0005 (tile size/scratch-disk budget); invariant §7.3.3 (history stores operations, not snapshots); PLAN.md M1.4 (crash-recovery journal's deferred on-disk half), M1.9

## Context

PRD §12 Q7 asks directly: "must `.aur` be forward-compatible across versions from v1.0? Decide before the first byte is written." Nothing has been written yet — `aurora-doc`'s crash-recovery journal (M1.4) and `aurora-app`'s crash-recovery marker (M1.8) have both already deferred real on-disk persistence specifically because no `.aur` encoding existed to persist to. `aurora-io`'s own PNG work (M1.9) reached the same wall from the other side: a real file format now exists for a single flat image, but the actual document — a `LayerTree`, a `History` journal, and per-layer pixel data potentially spanning up to the 300,000×300,000 px ceiling (ADR 0002) — has nowhere to go.

PRD §8.1's own technology table already narrowed the *serialization* half of this to two named candidates, `serde` + `postcard`/`rkyv`, but named no container shape and answered no forward-compatibility question — those are what this ADR actually decides. Three requirements shape the answer, not just picking a crate:

1. **§14's own consequence: "`.aur` is an open format. Specified and freely implementable, consistent with the local-first goal."** A format description that requires linking a specific Rust crate's own in-memory layout to read (as zero-copy formats like `rkyv` inherently do) is a much harder target for an independent, non-Rust implementation than one built from off-the-shelf, ubiquitous primitives.
2. **The 300,000 px ceiling and "unlimited layers/history" (PRD Scalability) mean whole-file parsing is not an option.** The same reasoning that makes PSD/PSB require lazy, streaming parsing ("open a 2 GB PSD in under 5 s") applies at least as strongly to Aurora's own format — a document must be openable, and individual layers/tiles randomly accessible, without holding the whole file in memory.
3. **`aurora-tile` already has a real, proven, versioned tile codec** (`codec::encode`/`decode` — `ATIL` magic, version byte, `lz4_flex` compression with a raw fallback for incompressible data, bit-exact round-trip proven in that crate's own tests). A document format needs to store bulk pixel data somewhere; inventing a second pixel encoding at the document level, instead of reusing the one that already works, would be redundant compression (paying the CPU cost twice) and a second thing to keep correct.

## Decision

**`.aur` is a ZIP archive** (via the `zip` crate, default features trimmed to just `STORE`/`DEFLATE` — no encryption, no `bzip2`/`lzma`/`zstd`/`ppmd`, none of which this format needs), holding:

- A first entry, `mimetype`, stored *uncompressed* — the same trick ODF/EPUB/OpenRaster (`.ora`) use so a magic-byte sniff can identify the format without parsing a full ZIP central directory.
- A manifest entry (document header: canvas size, colour space, and the full `LayerTree` structure — every `LayerId`/`LayerKind`/`BlendMode`/opacity/lock/mask/etc.) serialized with `serde` + **`postcard`**.
- A history entry: `History`'s own journal (`History::replay`'s log, M1.4), also `postcard` — this is what finally gives the crash-recovery journal (deferred in M1.4 and M1.8) somewhere real to be written.
- One ZIP entry per tile, storing `aurora_tile::codec::encode`'s own output **verbatim, stored without further ZIP-level compression** (it is already `lz4_flex`-compressed; compressing compressed bytes again wastes CPU for no size benefit, and `codec::decode` already handles its own header/fallback logic unchanged).

**Forward/backward compatibility policy (Q7's own question, answered directly):**

- **Backward, unconditionally**: every `.aur` file this project ever writes must keep opening in every future Aurora version. A breaking change to a metadata struct's shape is expressed as a new manifest schema (the postcard-serialized struct carries its own version field), with the reader supporting every past schema version it has ever shipped — never a hard cutoff.
- **Forward, best-effort**: an unknown ZIP entry (from a newer Aurora version a current build doesn't recognise) is skipped, not fatal — ZIP's own central directory already makes "list entries, read only the ones you understand" natural, so this costs nothing extra to support. An older Aurora opening a newer file loses only the parts it doesn't recognise, the same "degrade honestly, never silently" ethos already applied to lossy PSD saves (PRD §5), not a crash.
- Every write always uses the current format version; explicit "save as an older `.aur` version" compatibility export is out of scope here — not requested, no evidence it's needed yet.

**`postcard` over `rkyv`** for the metadata entries: `rkyv`'s zero-copy design ties its wire format to Rust's own in-memory type layout, in direct tension with §14's "specified and freely implementable" goal, and its real selling point — avoiding a deserialization pass over huge data — doesn't apply here, since the actual huge data (pixels) is handled separately by `aurora_tile::codec`, not by whatever serializes the comparatively small `LayerTree`/`History` structs. `postcard`'s simple, documented, `no_std`-friendly wire format is the better fit for something meant to be independently implementable.

### Optional entries added since (append-only)

Each is written only when it has something to say, so an ordinary save stays byte-identical to the previous version's; a file without it decodes exactly as before; and an older Aurora skips it as an unknown entry (the forward rule above).

- `skipped-tiles` — tiles a best-effort writer could not read.
- `mask-density` (0.149.0) — masks below full density, `postcard`, version first.
- `layer-effects` (0.180.0) — every layer's effects (`aurora_core::LayerEffects`, `#[serde(skip)]` in the manifest), `postcard` `{ version: 1, effects: [(layer id, effects)] }`, read through a 16 MiB cap and validated (`LayerTree::set_effects`). The payload is positional, so any change to the effects types is a new version, and **a version this build does not know refuses the open** rather than dropping the effects silently. An Aurora older than 0.180.0 skips the entry, but refuses any file whose journal holds the appended `SetEffects` op.
- `smart-objects` (0.200.0) — preserved Photoshop smart objects: `postcard` `{ version: 1, objects: [(layer id, aurora_doc::SmartObject)], files: [{ list, unique_id, len }] }` (`SmartObject` is `#[serde(skip)]` in the manifest), read through an 80 MiB cap and validated (`LayerTree::set_smart_object`, `add_linked_file`), plus one **stored** (uncompressed) entry `smart-object-file-<n>` per embedded file holding the PSD's framed linked-layer entry verbatim, each read through a cap equal to its recorded length, checked to be a well-formed frame, and charged against a 512 MiB pool bound. Written only when the document has smart-object data, so every other save is byte-identical. Positional, so any change to `SmartObject` is a new version, and **a version this build does not know refuses the open**; a missing or damaged file entry refuses it too. An Aurora older than 0.200.0 skips the entries but refuses any file whose journal holds the appended `SetSmartObject` op (ordinal 17). The cost is size: the embedded files travel in every save and autosave.
- `layer-clipping` (0.201.0) — which layers are clipped to the layer beneath them: `postcard` `{ version: 1, clipped: [layer id] }` (`LayerEntry::clipped` is `#[serde(skip)]` in the manifest), written only for layers that have an unclipped layer beneath them in their group, so every other save is byte-identical; read through a 16 MiB cap, each id applied by `LayerTree::set_clipped` (a missing layer, a group or a layer with nothing beneath it refuses the open); **a version this build does not know refuses the open**. An Aurora older than 0.201.0 skips the entry but refuses any file whose journal holds the appended `SetClipped` op (ordinal 18).
- `import-losses` (0.177.0) — the lines of a PSD's "Opened With Changes" report for a document opened from another file, `postcard` `{ version: 1, lines }`, so a later Photoshop save of the document still lists what its open dropped after a `.aur` save or a crash recovery. Read as untrusted data: at most 256 lines of at most 1,024 characters, control and text-direction characters dropped (the layer-name rule), and any decode problem — an oversized, damaged, empty or unknown-version entry — reads as one generic line ("This document was opened with changes from another file."), never as none, so it errs towards asking. **Known limit (0.177.0 review, L-5):** an Aurora older than 0.177.0 that opens and re-saves such a file drops the entry, so a later PSD save from 0.177.0+ over the original would not list those losses. That needs a deliberate downgrade, and older versions cannot write PSDs themselves.

### Appended enum variants (format notes)

`postcard` encodes an enum as its variant index, so new variants are always appended, never inserted: an older file then decodes unchanged. A **newer** file that uses an appended variant is *not* readable by an older Aurora — its decoder sees an unknown index and refuses the whole entry — and that is a clean failure, not a silent one: the open is refused with "Couldn't Open File" (0.143.1), and the current document is untouched.

- `LayerKind::Adjustment` (0.155.0) — an Aurora before 0.155.0 refuses a file holding a Curves layer.
- `BlendMode::PassThrough` (0.179.0, ordinal 27, valid on groups only) — an Aurora before 0.179.0 refuses a file holding a Pass Through group, and a crash-recovery journal holding a `SetBlendMode` to it. Pinned by `aurora-doc`'s `old_blend_mode_bytes_decode_unchanged_and_an_old_reader_refuses_pass_through`, which decodes the new bytes with a copy of the 27-variant enum. A current Aurora refuses a decoded tree that puts it on a pixel or adjustment layer (`DocError::GroupOnlyBlendMode`). A file opened from a PSD with Pass Through groups therefore saves to a `.aur` only this version and later can read; there is no "save for an older Aurora" export (the rule above).
- `Adjustment::Levels(LevelsParams)` (0.202.0) — appended after `Adjustment::Curves` (ordinal 1 inside `LayerKind::Adjustment`, which is itself ordinal 2). Wire: `LevelsParams` is four `LevelsChannel` records (master, red, green, blue), each a tuple of five `f32` `(input_black, input_white, gamma, output_black, output_white)` (80 bytes); a record failing `LevelsChannel::new`'s validation (non-finite, outside `[0, 1]`, input white less than one 8-bit level above black, gamma outside 0.10..9.99) is a decode error, never repaired. Files without a Levels layer are byte-identical; an Aurora older than 0.202.0 refuses a file (manifest or journal) holding one, as the unknown ordinal fails the decode. No manifest version bump.
- `Adjustment::HueSaturation(HueSaturationParams)` (0.203.0) — appended after `Adjustment::Levels` (ordinal 2 inside `LayerKind::Adjustment`, which is itself ordinal 2). Wire: `HueSaturationParams` is a tuple of seven values `(hue, saturation, lightness, colorize, colorize_hue, colorize_saturation, colorize_lightness)`: six `f32` and one `bool`, 25 bytes; a tuple failing `HueSaturationParams::new`'s validation (non-finite; master hue outside -180..180; master saturation or lightness outside -100..100; Colorize hue outside 0..360, saturation outside 0..100, lightness outside -100..100) is a decode error, never repaired. Files without a Hue/Saturation layer are byte-identical, and Curves and Levels bytes are unchanged (pinned by `aurora-doc`'s `curves_and_levels_bytes_are_unchanged_and_an_old_reader_refuses_hue_saturation`, which decodes the new bytes with a copy of the 0.202.0 two-variant enum); an Aurora older than 0.203.0 refuses a file (manifest or journal) holding one, as the unknown ordinal fails the decode. No manifest version bump. The per-colour-range adjustments are not in this tuple: they are the appended variant below (0.204.0).
- `Adjustment::HueSaturationRanges(HueSaturationRangesParams)` (0.204.0) — appended after `Adjustment::HueSaturation` (ordinal 3 inside `LayerKind::Adjustment`). Wire: a tuple `(HueSaturationParams, [HueRange; 6])`; a `HueRange` is a tuple of seven `f32` `(edge1, edge2, edge3, edge4, hue, saturation, lightness)` (28 bytes), so the variant is 25 + 6 x 28 bytes after its ordinal. A range failing `HueRange::new` (non-finite; an edge outside 0..360; the forward gaps edge1->edge2->edge3->edge4, each modulo 360, summing to more than 360; hue outside -180..180; saturation or lightness outside -100..100) is a decode error, never repaired. A layer whose six ranges are Photoshop's standard edges adjusting nothing is written as ordinal 2 (`Adjustment::from_hue_saturation`), so the 0.203.0 bytes are unchanged (pinned by `aurora-doc`'s `ranged_hue_saturation_is_ordinal_three_and_plain_stays_ordinal_two`, which decodes with a copy of the 0.203.0 three-variant enum); an Aurora older than 0.204.0 refuses a file (manifest or journal) holding ordinal 3. No manifest version bump.
- `Adjustment::Vibrance(VibranceParams)` (0.239.0) — appended after `Adjustment::HueSaturationRanges` (ordinal 4 inside `LayerKind::Adjustment`). Wire: a tuple `(vibrance, saturation)` of two `f32`, 8 bytes; a tuple failing `VibranceParams::new`'s validation (non-finite; either value outside -100..100) is a decode error, never repaired.
- `Adjustment::Exposure(ExposureParams)` (0.239.0) — ordinal 5. Wire: a tuple `(exposure, offset, gamma)` of three `f32`, 12 bytes; exposure outside -20..20, offset outside -0.5..0.5, gamma outside 0.10..9.99 or a non-finite value is a decode error.
- `Adjustment::PhotoFilter(PhotoFilterParams)` (0.239.0) — ordinal 6. Wire: a tuple `(red, green, blue, density, preserve_luminosity)`, four `f32` and one `bool`, 17 bytes; a colour channel outside 0..1, a density outside 1..100 or a non-finite value is a decode error. All earlier adjustment bytes are unchanged (pinned by `aurora-doc`'s `earlier_adjustments_keep_their_bytes`, which encodes with a copy of the 0.238.0 four-variant enum, and `the_new_adjustments_are_ordinals_four_five_six_and_an_old_reader_refuses_them`); an Aurora older than 0.239.0 refuses a file (manifest or journal) holding ordinals 4, 5 or 6. No manifest version bump. (Corrected in 0.246.0: PSD save of these layers was refused by name until 0.241.0; since then the writer writes them as `vibA`, `expA` and `phfl`.)
- `Adjustment::BlackWhite(BlackWhiteParams)` (0.240.0) — ordinal 7 inside `LayerKind::Adjustment`. Wire: a tuple `(weights, tint, tint_hue, tint_saturation)`, six `f32` weights (reds, yellows, greens, cyans, blues, magentas), one `bool` and two `f32`, 33 bytes; a weight outside -200..300, a tint hue outside 0..360, a tint saturation outside 0..100 or a non-finite value is a decode error, never repaired.
- `Adjustment::ColorBalance(ColorBalanceParams)` (0.240.0) — ordinal 8. Wire: a tuple `(shadows, midtones, highlights, preserve_luminosity)`, each range three `f32` `(cyan-red, magenta-green, yellow-blue)`, then one `bool`, 37 bytes; a slider outside -100..100 or a non-finite value is a decode error. Ordinals 0 to 6 are unchanged (pinned by `aurora-doc`'s `ordinals_zero_to_six_keep_their_bytes`, which encodes with a copy of the 0.239.0 seven-variant enum, and `the_new_adjustments_are_ordinals_seven_and_eight_and_an_old_reader_refuses_them`); an Aurora older than 0.240.0 refuses a file (manifest or journal) holding ordinals 7 or 8. No manifest version bump. (Corrected in 0.246.0: PSD save of these layers was refused by name until 0.241.0; since then the writer writes them as `blwh` and `blnc`.)
- `Adjustment::{Invert, Threshold(ThresholdParams), Posterize(PosterizeParams), BrightnessContrast(BrightnessContrastParams)}` (0.244.0) — ordinals 9, 10, 11 and 12, appended after `ColorBalance`. Wire: `Invert` is the ordinal alone; `Threshold` is one `u8` level (1..255) and `Posterize` one `u8` level count (2..255); `BrightnessContrast` is a tuple `(brightness: i16, contrast: i16, use_legacy: bool)` of zig-zag varints and a byte, brightness -150..150 and contrast -50..100 (both -100..100 when `use_legacy`). A value outside its range is a decode error, never clamped. Ordinals 0 to 8 are unchanged (pinned by `aurora-doc`'s `ordinals_zero_to_eight_keep_their_bytes`, which encodes with a copy of the 0.243.0 nine-variant enum, and `the_new_adjustments_are_ordinals_nine_to_twelve_and_an_old_reader_refuses_them`); an Aurora older than 0.244.0 refuses a file (manifest or journal) holding ordinals 9 to 12. No manifest version bump.
- `Adjustment::{ChannelMixer(ChannelMixerParams), SelectiveColor(SelectiveColorParams)}` (0.245.0) — ordinals 13 and 14, appended after `BrightnessContrast`. Wire: `ChannelMixer` is a tuple `(red_row, green_row, blue_row, monochrome)`, each row four `f32` `[red, green, blue, constant]` (sources -200..200, constant -100..100), then a `bool`: 49 bytes; `SelectiveColor` is a tuple `(ranges, absolute)`, nine rows of four `f32` `[cyan, magenta, yellow, black]` (-100..100; ranges Reds, Yellows, Greens, Cyans, Blues, Magentas, Whites, Neutrals, Blacks) then a `bool` (false Relative): 145 bytes. A non-finite or out-of-range value is a decode error, never clamped. Ordinals 0 to 12 are unchanged (pinned by `aurora-doc`'s `ordinals_zero_to_twelve_keep_their_bytes`, which encodes with a copy of the 0.244.0 thirteen-variant enum, and `the_new_adjustments_are_ordinals_thirteen_and_fourteen_and_an_old_reader_refuses_them`); an Aurora older than 0.245.0 refuses a file (manifest or journal) holding ordinals 13 or 14. No manifest version bump.
- `Adjustment::GradientMap(GradientMapParams)` (0.248.0) — ordinal 15, appended after `SelectiveColor`. Wire: a tuple `(stops, reverse, dither, method)` where `stops` is a sequence of `[position, red, green, blue]` `f32` arrays (a varint count of 2 to 64, then 16 bytes a stop; positions 0..1 non-decreasing, channels 0..1), `reverse` and `dither` are `bool`s and `method` a `u8` (`0` = Classic is the only value accepted; the byte leaves room for other interpolation methods without a new ordinal): 36 bytes for two stops. A non-finite or out-of-range value, a count outside 2..64 or an unknown method byte is a decode error, never clamped. Ordinals 0 to 14 are unchanged (pinned by `aurora-doc`'s `ordinals_zero_to_fourteen_keep_their_bytes`, which encodes with a copy of the 0.247.0 fifteen-variant enum, and `gradient_map_is_ordinal_fifteen_and_an_old_reader_refuses_it`); an Aurora older than 0.248.0 refuses a file (manifest or journal) holding ordinal 15. No manifest version bump.
- The `selection` entry (0.218.0) — an **optional, versioned** top-level entry holding the active selection and the named saved selections (`aurora-io`'s `aur_selection.rs`). Wire: a `postcard` header `(version: u32 = 1, active: Option<Meta>, saved: Vec<(String, Meta)>)` with `Meta = (x: i64, y: i64, width: u32, height: u32, inverted: bool, kind: u8)` (kind 0 rectangle, 1 ellipse, 2 raster mask; the bounds are the mask's own for a mask), saved selections sorted by name, followed by the raw row-major coverage bytes of every mask selection in header order (active first); the container deflates the entry. Written only when the document has a selection, so every other save is byte-identical; absent means no selection. **Reader rules:** a `version` greater than 1 refuses the open ("saved by a newer Aurora"), like `layer-effects`; version 0, a header that does not decode, an unknown kind, a name failing `validate_selection_name`, a repeated name, more than 64 saved selections, a mask over 64 Mpx, saved masks over 128 MiB, a blob size that does not equal the bytes that follow, an origin past 2^32, an entry over its read cap (64 Mpx + 128 MiB + 64 KiB) or unreadable **drop the selection and keep the file** (`AurDocument::selection_dropped`), because the selection is optional metadata and no layer depends on it; every size is validated from the header before any coverage is copied. An Aurora older than 0.218.0 never looks the entry up and ignores it (entries are read by name; tested), so no manifest version bump and no journal change. The PSD writer does not carry selections (a documented gap tied to alpha channels).
- `LayerOp::Translate { dx, dy }` (0.226.0, the Crop) — appended last in the journal's operation enum (an Aurora before 0.226.0 refuses a `.aur` or crash-recovery autosave whose journal holds one: loudly, never a wrong picture). It shifts every pixel layer's `bounds` and every layer's, group's and adjustment's mask `bounds` by `(dx, dy)`; tile contents are layer- and mask-local and are not touched. **No new entry and no manifest change:** the manifest already stores `canvas_width`/`canvas_height` and the layers' (shifted) bounds, so a crop smaller than its layers persists as it is. The shift is exact and invertible; undo is the same op negated.

- The `paths` entry (0.233.0) — an **optional, versioned** top-level entry holding the document's Bezier paths and its unsaved work path (`aurora-io`'s `aur_paths.rs`). Wire: one `postcard` value `(version: u32 = 1, paths: Vec<(name: String, subpaths: Vec<(closed: bool, anchors: Vec<[f32; 6]>)>)>, work: Option<(String, subpaths)>)`, an anchor being `[x, y, handle_in_dx, handle_in_dy, handle_out_dx, handle_out_dy]` in document pixels, saved paths in panel order, the work path last (always named "Work Path"); the container deflates the entry. Written only when the document has a path, so every other save is byte-identical; absent means no paths. **Reader rules:** a `version` greater than 1 refuses the open ("saved by a newer Aurora"), like `selection`; version 0, a value that does not decode, a name failing `validate_path_name` (or "Work Path" on a saved path, or another name on the work path), a repeated name, more than 64 paths, more than 256 subpaths or 10,000 anchors in one, more than 200,000 anchors in all, a non-finite coordinate or one beyond 1e7, or an entry over its read cap (200,000 x 25 bytes + 256 KiB) or unreadable **drop the paths and keep the file** (their reason is appended to `AurDocument::selection_dropped`), because paths are optional metadata and no layer depends on them. The entry is read through its byte cap before decoding, so the decoder never sees more than the cap and every element costs at least one byte. An Aurora older than 0.233.0 never looks the entry up and ignores it (tested), so no manifest version bump and no journal change. The PSD writer does not carry paths (a documented gap).

## Alternatives considered

**A hand-rolled binary chunk container** (RIFF/PNG-style: magic + version + a flat sequence of length-prefixed, typed chunks), the same shape `aurora_tile::codec` already uses one level down. Rejected in favour of ZIP specifically because ZIP already *is* that shape (a central directory is a chunk index), plus it comes with ubiquitous, battle-tested tooling in every ecosystem — a user can inspect a `.aur` file's contents with a file manager they already have, a real, tangible instance of "open format" a bespoke container wouldn't provide for free. Reinventing chunk framing, a table of contents, and a parser for it would be real, avoidable engineering effort duplicating what ZIP readers already do correctly.

**`rkyv` for metadata** — see Decision above; rejected on the "open format" goal and because its main advantage doesn't apply to the data it would actually be encoding.

**A single monolithic `postcard`-serialized struct for the whole document, no container** — rejected: no lazy/streaming access at all (the entire point of ADR 0002's 300,000 px ceiling and PRD's "open a 2 GB PSD in under 5 s" bar), and no clean forward-compatibility story — a newer field added to one giant struct either breaks every old reader or requires `#[serde(default)]` scattered everywhere with no room to skip a whole *unrecognised feature* the way an unknown ZIP entry can be skipped outright.

**Deferring the decision further, waiting for more evidence** — rejected: PRD §12 Q7 explicitly frames this as a "decide before the first byte is written" question, and two real subsystems (the crash-recovery journal, `aurora-io`'s own PNG work) are already blocked on exactly this gap; there is no additional Phase 0-style spike evidence this decision is waiting on the way RAW/ICC's library choice was.

## Consequences

**Gained:** a real place for the crash-recovery journal (M1.4/M1.8's own deferred "no on-disk encoding decided" gap) to finally write to; lazy/lazy-enough streaming access matching the 300,000 px ceiling, via ZIP's own central directory rather than a hand-built index; reuse of `aurora-tile`'s already-proven, already-tested tile codec rather than a second pixel encoding; a genuinely third-party-implementable format (any language with a ZIP library and a `postcard` decoder — or just enough of `postcard`'s simple wire format description to hand-write one — can read a `.aur` file), matching PRD §14's explicit design goal; real, proven precedent in the exact same problem domain (Krita's `.kra` and OpenRaster's `.ora` are both ZIP-based layered-image containers), not a novel approach with no track record.

**Cost:** a ZIP container has real overhead a bespoke format wouldn't (a central directory, per-entry headers) — negligible next to tile-sized payloads, but not zero. `postcard`'s own schema evolution is manual, not automatic: every future breaking change to a manifest/history struct's shape needs a deliberate new version handled explicitly in the reader, not a framework that does it automatically (`rkyv`'s archived-type approach has the same property, so this isn't a comparative cost, but it is a real, ongoing discipline this project now owns). Encrypting or otherwise protecting a `.aur` file's contents is not addressed by this decision (not asked for; the `zip` crate's `aes-crypto` feature exists if ever needed, deliberately not enabled now).

**Follow-on work:** the actual container reader/writer implementation (a real, separate `aurora-io` module — this ADR decides the shape, not the code); deciding the manifest schema's exact field-by-field layout for `LayerTree`/`History` (real design work, not fully specified here); wiring `aurora-doc`'s crash-recovery journal to actually write through this format (M1.4's own follow-on); deciding autosave frequency/granularity (a separate M1.9 bullet); the real question `aurora_doc::LayerKind::Pixel`'s own doc comment already named and this ADR doesn't resolve — whether pixel storage is one `TileStore` per layer or one shared store addressed some other way — which the manifest's own per-layer tile-addressing scheme will need an answer to, not before. **Resolved 2026-08-06 by [ADR 0010](0010-layer-pixel-storage.md)**: one shared `TileStore` per document, addressed by a `SurfaceId` reused from each pixel layer's own `LayerId` — the manifest's tile-addressing scheme can now name a tile's ZIP entry by its `(SurfaceId, TileId)` pair once the reader/writer above is actually implemented.

## Reconsider if…

- A real non-Rust reader implementation hits genuine friction with `postcard`'s wire format specifically (unlikely — it's a simple, documented varint-based format — but not yet tried by anyone outside this project)
- `aurora_tile::codec`'s own on-disk format changes in a way that stops being safely embeddable as an opaque ZIP entry (e.g. if it ever needs random access *within* a tile's own payload, which stored-whole-tile access doesn't provide)
- A future, genuinely huge-single-session workload (e.g. real-time collaborative editing, PRD's own "Beyond v1.0" territory) needs a append-only or memory-mapped access pattern ZIP's central-directory-rewrite-on-update model serves poorly — at that point, `rkyv`'s zero-copy mmap story or a purpose-built log-structured format become worth re-evaluating against the "open format" cost they'd bring back
